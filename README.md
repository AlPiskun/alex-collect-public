# Alex Collect 2.98

Alex Collect is a local desktop control panel for organizing a small trading-card selling workflow. It brings together the card pipeline, WooCommerce order inputs, customer quotes, a sale checklist, photo utilities, and optional plugins.

## Core features

- Run the card pipeline from a Tkinter desktop window.
- Preview the orders that sold since the last check, then add only those to the sale checklist.
- Compare stock between the website and CanadianShopper, eBay or Facebook on demand, and do something about what you find. The list holds only what needs attention - a count that differs, a card whose listing on the other site is not on sale, or a card that exists on one side only - and it is where the fixing happens: a card sitting at **zero on the website** that the other site does not list either is not shown at all, because there is no count to set and a listing at zero cannot be bought; the summary says how many were left out, so a card never simply vanishes. The list opens in the order that needs attention first and can be re-sorted from the chooser above it - what needs attention first, card name either way, the biggest difference, or the most stock on either side - and the choice is remembered with the other settings. Reading shows a progress bar: a real page count when the site's own headers state one, a sweep for a marketplace whose page has to be read in one go, and the website's catalogue is read **four pages at a time, in order**, so a 2,500-card shop waits for a quarter of the round trips it used to. the website is right far more often than not, so one button sets every differing CanadianShopper count to the website's count, always showing the exact card, the old count and the new one and asking first. Select rows to fix or ignore just those, and when the website is the one that is wrong, **Set the website to the selected cards' counts...** writes the other site's count onto the website product - one field, `stock_quantity`, one product at a time, with its own confirmation naming each card and both counts, stating the direction outright and naming the side that is not touched, and the website's answer read back so a 200 that quietly kept the old number is reported as a failure. That direction needs WooCommerce keys with Read/Write access (the same pair the photo wiring uses); a read-only pair is told apart from a broken one, and the cards stay on the list because nothing was written. **Open the selected cards on the website** is still there for a count a plugin owns or a variable product, where a number is not the whole story. A listing that **exists but cannot be bought** gets its own row and its own words - draft, archived, hidden, out of stock, in the vendor's own spelling - because a stock count cannot fix it: CanadianShopper's `stock.set` only touches listings that are on sale, so those rows are never written to. Every listing the reader reports is kept, including one that carries no stock count at all: a listing with no number still exists, and dropping it is how a card that is really there comes back as only on your website. A live listing with no number gets its own row - *on CanadianShopper but no stock count there* - never a made-up zero and never a write; the fix is on that listing (turn its stock tracking on) or ignore the card. A draft with no stock is still a draft. When any of the not-on-sale cards is a draft, **Publish the ready drafts...** is offered beside the list (the same publisher, with the same readiness checks and the typed PUBLISH); a hidden or archived one has to be dealt with in the vendor dashboard. Plugin 1.0.25 or newer reports each listing's status, including the ones that are not on sale - before that the comparison simply could not see them, which is why cards that already existed kept being offered as missing; 1.0.26 or newer also proves the page it read was not a cached one.
- A card that is on the website and no longer on CanadianShopper is the one that can be put *back*: select it and **List the selected cards on CanadianShopper...** writes the same import file the batch pipeline writes - the same fourteen columns, the same filename, the same folder - built from the website product itself (its title, its price, the photo URL the shop already serves, its stock count), with the confirmation naming each card and anything missing from it (no photo, no price, or a card at zero that would be listed out of stock). The file is written first, then Alex Collect offers to import it for you: with plugin **1.0.23 or newer** (`marketplace.import_csv`) the draft listings appear without leaving the app, while a plugin without it says so and opens the folder, because the file is the same one a batch produces either way. Imported listings always arrive as unpublished drafts, and the run then offers the step that actually puts the card back on sale: **publish the new drafts**, which is the existing publisher with `--apply`, so the readiness checks still decide what may go live and PUBLISH still has to be typed. That publisher scans every draft on CanadianShopper - the dialog says so - so drafts from earlier runs are considered too and anything not ready is left alone; If the import created nothing because every row already exists on CanadianShopper, nobody yet knows whether there is a draft to publish, so Alex Collect asks the publisher to **look first**: one read-only scan, and the typed PUBLISH question is only asked once that scan reports a draft. The publisher's own line decides that - *Drafts found: 0* - not the shape of its report file, which is the plugin's format: a file with a header and a summary line in it is still no drafts. Finding none is an answer too - there is nothing to publish, an empty report is not offered (the publisher writes one row per draft, so no drafts means no rows), and the console names the cards it could not find, so the dashboard search has something to search for. It also says what is left: a listing that exists but is not a draft is hidden, archived, private or off sale, or a variation of a variable product, and those are put back on sale in the vendor dashboard. A stock reader older than plugin **1.0.25** is named by version at the end of the comparison too, because it reports only the listings that are on sale - which is exactly why cards that already existed kept looking missing. Declining a publish falls back to the read-only *Preview drafts* report. A card that comes back one-sided is diagnosed rather than just reported: the nearest title on the other site is looked up with the same weighing the pairing uses (and the same card-number rule, so a different card number is never a "near miss"), and the console either shows that listing with its score and the website product it already belongs to, or states that nothing similar is there at all. That is what tells the three cases apart: worded differently, already held by a duplicate product of the same name (a listing cannot be shared, so the duplicate - not the card - is what does not exist), or genuinely not listed, where the import is what creates it. When two website products score identically, the one that can actually sell holds the listing, so a sold-out copy can no longer take it and leave the live product looking missing. Two titles that name **different conditions** (VG against PR, EX against EX-MT) are never paired, however alike the rest of the words are: they are two items selling at different prices, and pairing them would write one copy's count onto the other copy's listing. A listing that states no condition still pairs as it always did. The reader's own states are printed after every read, with the reader that produced them - *What the reader returned (plugin 1.0.26, cache-checked) - 2514 listing(s): 2509 on sale, 5 Archived* - so a page the site served from its cache can be told apart from a real change. Plugin **1.0.26** asks for a page the site cannot serve from its cache and re-reads once when a page comes back byte-identical to the last run; with anything older the panel says so instead, because a listing moved in the vendor dashboard could otherwise keep coming back in its old state - and the app would be blamed for repeating what it was given. The version is read from the plugin, never assumed: an unreadable one gets no claim either way. A listing the other site holds at **zero** is called what it is: the listing exists, it just cannot be bought, and setting the counts is what puts the stock back. The cards stay on the list until the next comparison finds them live on CanadianShopper. **List every website-only card...** does the same for the whole list at once. A card that is no longer sold on the other site is ignored rather than asked about forever: the dismissal is remembered in `stock-ignored.json` and a dismissed card comes back if its title is edited or when you restore it. Comparing changes nothing on any site, and only the counts are ever written - nothing is added, removed or repriced. Writing the CanadianShopper count is plugin 1.0.21 or newer (`stock.set`); the count is sent as `{"inventory": n}` and nothing else, matched by listing id, then SKU, then title, and a card the plugin could not match or found ambiguous comes back as failed with its reason - the row stays on the list, because a count the plugin did not confirm is not a count that was fixed. An older plugin is told apart from a failure: the dialog names 1.0.21 and the exact changes go to the clipboard and the console.
- Find one CanadianShopper listing by its card and change it there, without opening the vendor dashboard. Type the name the way you remember it - `tkaczuk 25`, a SKU or a listing id all find it, weighed the same way the order panel weighs a customer's line - or leave the box empty and pick a state to work through the archived listings one by one. Every row is numbered and reads card, state, stock, price and SKU. Select one and **Edit the selected listing...** opens all of its details at once in one form - title, price, quantity in stock and state - filled with what they are now, so a card can be repriced and archived in the same visit; the two state buttons do just the state, which is the quick way through a restock. The listing's own page opens for the details this panel does not edit (description, photos) - plugin 1.0.29 sends an absolute address for every listing it can, and any spelling of that address (`url`, `link`, `permalink`, `href`, `productUrl`, ...) is understood; if there is no usable address at all, your store opens instead and the card and its listing id go on the clipboard to search for. Every change is named field by field before it is sent - *Stock: 3 -> 5*, *State: archived -> on sale* - and only the fields that changed are sent (with the title, which is how the plugin finds the listing), so an edit cannot put back a value that was changed in the dashboard while the panel was open. It writes on CanadianShopper only: your website's title, price and stock are not touched, and archiving puts a listing away rather than deleting it. Reading needs the plugin's stock reader, editing needs plugin **1.0.28 or newer** (`marketplace.listing_update`). Every id the reader reports travels with the edit - the product id beside the listing id - and a write that comes back "not found" prints how the plan named the listing and says the site was not changed, because that is the one fact needed to fix it. The panel says which plugin read the list on screen and how much of it can be written ("12 listings read; 12 with a product id, so 12 can be edited here"), and tells the two ways a row can lack a product id apart: a row that has none while others do gets a re-read, then the same change from the fresh row, asked once more before it is written; a reading in which *no* listing carries one - which is the reader's gap, not 2,541 cards to fix by hand - says so plainly, offers no pointless second read, and opens the listing's own page so the change can be made on the site. - without it the panel says so and changes nothing.
- Read eBay and Facebook without being lied to about what came back. Both sites check whether a request comes from a browser: eBay answers with its "Pardon our interruption" page under HTTP 200 and Facebook with an HTTP 400 script shell. The panel names that page, says your cookie is not the problem and that nothing was read or changed, and then does the thing that actually works: **the page saved from a signed-in browser is found by the app itself**, in its own folder and in Downloads, newest first, recognised by what is in it rather than by its filename - a browser names the file after the page's title. **Read the saved eBay/Facebook page** needs no file picker, **Choose a saved page...** is there for the rare case of wanting a different one, and a refusal no longer stops a comparison: the newest saved page is read into it automatically and the console says which file and which day it came from. Every live read also writes the app's own copy (`ebay-active.html`, `fb-selling.html`) from the page the site really sent, so there is always a fresh one to fall back on. eBay is read up to **250 listings** - the whole of a free store, and two pages of the 200 eBay serves - with every page kept in that copy rather than only the last. Facebook renders its first batch and lazy-loads the rest, so a request sees a window: when a page saved from a browser after scrolling holds more than the live read, that page is the one compared, and the console says how many the site sent beside how many the saved page holds. A page that loads but yields no listing is reported as "no listing on it could be read" with the saved copy named, never as an empty shop, and a page that is really a sign-in page is reported as an expired session so you know which fix to reach for.

- Configure the store URL, AI page, preferred browser, prompt preferences, custom AI commands, seller links, output/scanner folders, Facebook workbook fields, and eBay Quick List templates/defaults from **User Settings** in the menu bar. Its **Save user settings** button sits beside the title, in a strip above the form that does not scroll - the settings page is the longest in the app, and saving used to mean scrolling past every field first. The page is split into ten groups - when the app opens, the store and AI, the store pages, custom AI commands, marketplace pages, the eBay handoff, the Facebook fields, the CanadianShopper CSV, the folders, and the CanadianShopper login - and each group has its own heading and its own **What this panel does** button covering just that group, instead of one explanation trying to describe the whole page. Each page now fills the window rather than stopping at the height of its own widgets, and the output console takes fewer lines on a small screen, so a long form has the room to be scrolled through.
- Copy the built-in **Add grades to titles** and **No grades in titles** prompts, or create, edit, and remove custom AI command buttons in User Settings; hover notes clarify each command’s purpose.
- Review the initial nine-card category plan in compact one-row-per-card output; the larger, screen-adaptive console keeps the confirmation visible without scrolling.
- Use the compact task launcher with fixed-width buttons in four clearly separated sections - **Sell to a customer**, **Sell a new batch**, **After a sale** and **Photos**; the staging, draft-importing and photo-wiring buttons are gone from it, because the pipeline does those steps itself and **Re-run a marketplace step** repeats any that needs it. There is no extra headline above the buttons. Plugins and Logs & reports are direct menu items. Hover task buttons for short tips. The output pane always follows new output and entered replies so prompts remain visible.
- Every panel leads with its work: buttons and input fields sit together at the top, and the explanation is folded behind a **What this panel does** button beside the title - it opens directly under that row, so the answer appears where the click was, and it starts folded. A panel is opened to do something with it, not to read eight lines first - and at 800x600 the prose used to push the buttons off the bottom of the window. Long steps now say so while they run instead of leaving the window blank, and no window opens bigger than the screen it opens on. In the tabs view each panel sits in its own bordered, titled section with a gap between boxes, so a group holding five panels no longer reads as one long page. Every button in the app explains itself on hover - what it does and what it leaves unchanged - not only the ones on the task page, and a check fails the build if a new button ships without its sentence. Closing the panel help takes its frame out of the layout rather than leaving a gap where the words were, and the scrolling page area is painted in the window's own colour instead of Tk's default white, so a short panel ends where its content ends instead of trailing a white band. The page's scroll bar is drawn from the moment the window opens, not only after the window has been resized: the page is measured again once its content exists - and whenever that content grows - because Tk reports nothing when a frame pinned to the height of the window gains content inside it, which is what left a fresh window showing a full trough and no thumb.
- A card named after a printing variant keeps its front image. A dark-back card's photo titles carry the variant word *and* the side - `...-Kings-dark-back-front` - so the name contains `-back` twice; the side is now read from the **last** marker only, which is what it is. Before that fix the front title was dropped as "a front and back joined together" and the front image of every dark-back card was never renamed.
- Marketplace results are separated into Facebook, WooCommerce, CanadianShopper, and eBay folders. Woo/CS CSVs and eBay Quick List pages roll older batches into history on their next output run. - The pipeline opens the page the next step happens on, not the one it used to. Once the products are created it opens the **product list** (`wp-admin/edit.php?post_type=product`), which is where a batch is checked as published - the media upload page is opened only when the batch was imported by hand and its renamed images still have to go up. Once the Facebook exports are written it opens **Facebook's bulk-create page** (`https://www.facebook.com/marketplace/create/bulk`), the page the CSVs are fed through, instead of the selling list - that list is read for stock and has its own setting, so one can be changed without breaking the other. The workbook and its folder still open beside it.
- When a Facebook helper fails, its own words reach the console and a run that skipped a step no longer ends as though it finished. The feed history tracker and the Marketplace xlsx export run with pipes Alex Collect owns, unbuffered, with no console window of their own and never on the app's stdin, so whatever they printed - a traceback included - arrives line by line instead of being lost to a handle the child could not reach. A helper that says nothing at all is read as a launch problem rather than a mystery, and gets one turn on the app's own interpreter; if it still fails, everything either attempt printed is saved to `facebook_merchant_products/helper_last_run.log` and the path is printed. The exit code is spelled out in words instead of a number - *Windows stopped it from outside (0xC000013A)*, *it stopped on an error of its own*, *it crashed inside itself* - and the run ends with a **NOT EVERY STEP FINISHED** block that names the step, says what was still written, and returns a failing exit code, so the console cannot show *finished (OK, exit code 0)* over a missing workbook. That last part matters: a failed export leaves the previous `facebook_delta_<date>.xlsx` sitting there under a name that looks current, so the console now says outright that the workbook in the folder is the earlier one and does not include this batch. Both workbooks the step writes are tested before the feed is requested at all: one Excel is holding open (a write lock, which would otherwise surface as a permission error at the very end) is named by path with the words *close them and run the step again*, and the step stops there having changed nothing. And when the step runs from inside Alex Collect, where nothing is at the keyboard, it says so after its Enter-to-continue question instead of appearing to answer itself.
- Create the batch's products directly on the website, without WP All Import. The run shows a **progress bar** above the console for this step, because it is the slow one: it moves card by card and says which part is running - uploading the photos, creating the draft and reading it back, wiring the photos to it, putting it on sale - so a batch that is waiting on the site never looks like a batch that has stopped. The bar is fed by the pipeline itself (a marker the app strips from the console; when the same script is run in a terminal it prints plain `[3/9] Card name` lines and no markers), and it is put away when the run ends. Before the batch runs, Alex Collect asks what to do with the products and shows the same explanation every other write in the app shows: with the WooCommerce keys saved it creates each card as an **unpublished draft**, uploading the renamed front and back photos **before** the product exists, and it reads every product back from the site - its id, its SKU and its status - before reporting it as created, so a 200 that quietly kept a draft is reported as a draft rather than as success. A card whose SKU is already on the site is skipped, so running the same batch twice never duplicates it - and the report says what state that product is in, because *already there* is not the same as *on sale*: a product that is live is left alone, while a draft the batch is asked to publish is finished rather than left behind (never one with an empty gallery - a draft with no photos is named, with what to do about it). Publishing is its own step and only ever follows the photos: choose **put them on sale when the photos are on** and each product goes live the moment its gallery is complete, while a product whose photos did not upload stays a draft and the report says why; choose **as drafts** and they wait for you. Without the WordPress username and Application Password (lines 4-5 of `woo-keys.txt`) the products are still created, they just never publish themselves. Each photo the batch uploads is given its new product as its parent in the media library once the product exists, so a finished batch no longer leaves its pictures under **Unattached**; a site that refuses that one request has still made a finished product, so the report names it as a label on the library rather than as a failed card. Categories are reused when the site already has them and created parent-first when it does not, and one card failing never stops the rest - a card the site refused is reported with the site's own words. A rejected key pair stops the batch at the first card, names the pair as read-only or wrong, and marks the remaining cards *not attempted* instead of pretending they were. Nothing is ever deleted or repriced. When the keys are **not** saved the batch does not silently fall back to the CSV: it says so, opens `woo-keys.txt`, and asks again when you come back - and if you would rather not, the CSV is written either way. It stays the record, the WP All Import fallback, and what the Facebook and CanadianShopper steps read; every product that was created is also written to `woo-create-result.json` beside it.
- When the website answers with its own error page, the batch survives it and says where every card stands. A WordPress fatal reaches the app as HTTP 500 with one sentence for everybody - *There has been a critical error on this website* - which says nothing about what went wrong; the real cause is in the site's PHP error log, and on a batch like this it is usually the PHP memory limit or a request timeout. So the app no longer guesses. A read that decides whether a card already exists is repeated up to three times before the card is given up on, because one of the failures in the run this was written for was a single read of the product list. A product the site *wrote and then lost the answer to* is found again by its SKU and reported as created, never sent a second time, and a 500 whose SKU really is not there afterwards is called not created - with the words that say the error page hides the cause, that the keys are not the problem, and where to look. A card that was created but that the site would not publish is no longer called *not created*: it is *Not on sale*, with its product id and the site's own answer, because that one sentence is what invites a second copy through WP All Import. A card whose existence could not be read at all is *Could not be confirmed* - never missing - and three error pages in a row stop the run touching the site, naming what it did not attempt. The batch then ends as a failed step in the same **NOT EVERY STEP FINISHED** block as a broken Facebook helper, so a half-created batch cannot report exit code 0, and the way out is one instruction instead of a CSV: run the same batch again (**Re-run a marketplace -> WooCommerce CSV**, choosing to put the products on sale). It rebuilds from the AI text already on disk - the scans are not needed - looks every card up by SKU, publishes the drafts whose photos landed and creates only what is missing. The old *import the CSV* advice is kept only for a batch that wrote nothing at all, since importing it over cards that are already on the site is how duplicates appear.

The small pictures are kept for the sitting too, so the second card's picker opens at once instead of decoding them again. Images already used are no longer offered. Choosing an image means looking at it: the picker shows the card pictures captioned with nothing but the slot they came from - nine of them on an 800x600 screen, in a grid that scrolls if the window is smaller - with the buttons above the grid so they never scroll out of reach, and the back is proposed from the same slot on the back sheet because both sheets were filled in the same order. Then type the card name or SKU and Alex Collect opens the matching product edit page (with read-only API keys saved) or, when nothing matches, the filtered product list - and the photos you choose are still split, named from the scan and saved, so a card that is not on the website yet can be prepared in advance. Once the pair is on the product, each uploaded file is also given that product as its parent in the media library, so the photographs stop being filed under **Unattached** there: the product showed them either way, but a finished card whose pictures still say unattached reads like an upload that stopped half way. When a product's photos predate the `-front`/`-back` naming there is nothing to read the old back from, so Alex Collect asks which photo it is instead of guessing and leaving it beside the new one; that question also offers keeping every existing photo, and the confirmation then lists exactly what comes off and what stays. CanadianShopper plugin 1.0.15 or newer can then replace that one listing's photos with no staged CSV. From plugin 1.0.16 the new back replaces the old one, so a listing ends up with one front and one back; 1.0.15 is sent the front alone and told why, because its back would be added beside the old photo instead of replacing it, and anything older is told to update rather than being sent an argument it cannot honour. A listing's main photo is kept apart from its gallery, so one gallery row is not a one-photo listing - it can be an old back, a certificate, or packaging. Alex Collect never guesses which: from plugin 1.0.17 it asks, showing the row filenames and the images being sent, so you pick the row to replace, keep every row and add the new back beside them, or cancel. Closing that window without answering cancels, so a stray click changes nothing. - Turn a customer's texted list of cards into a website order from **Order from a text list**: paste the list and Alex Collect matches each line to a real product and writes a **pending** order - nothing is charged and no email is sent. One card per line, whether it is written `1970-71 O-Pee-Chee Paul Henderson #217` or `#217 Paul Henderson 1970-71 O-Pee-Chee` - numbering, bullets, bracketed notes and a trailing price are ignored, and a line beginning with a card number is a card, not a comment. You are asked whether to start a new order or add to an existing one by its number (cards already on it gain quantity rather than appearing twice). - Price a customer's cards for them from **Quote for a customer**, without creating anything: the quote is a document, and only its last button writes - a **pending** order, nothing charged and no email sent. Only cards the shop says are **in stock** are offered - a quote is an offer to sell, so a card that cannot be bought is not a result, and the line above the list says how many matches were left out for being out of stock rather than quietly dropping them. The matches can be sorted by name, cheapest first, dearest first or newest first, from a chooser beside the list; sorting only re-orders what is already there, and the choice is remembered for the next quote. **Add the selected card** takes one row, and **Type a card in by hand** takes a title, a card number and a price for something that is not on the website, so a quote can be built with no keys at all. The quote carries a number (`Q-2026-0001`), the customer's name, address, email and phone, notes, and an optional discount as a percentage or a flat amount, and it shows how many cards and how many items with the prices added up - a discount larger than the subtotal clamps to zero rather than going negative. Every row can be re-priced from the website, which names each price that moved before changing anything, because a quote is a promise to a customer. The PDF is A4 with your own logo and colour, a band at the top carrying the shop name and the quote number, one line per card, the discount and the total, a `Page N of M` footer, and a second page when the cards overrun - the type is never shrunk to force them onto one. The quote is saved as its own numbered file beside its PDF (`quotes/Q-2026-0001.json`), so it can be reopened, adjusted, re-priced and printed again weeks later, and the date it is valid until travels with it. **Turn into an order...** is the order writer the texted-list panel already uses: the shop's cards are read again first, a price that moved since the quote is named as a difference before anything is written, the discount goes on as one fee line, the quote number goes into the order note and into a `_alex_quote` meta value, and the order arrives pending. The printed quote carries **a picture of every card** beside its name, downloaded once and kept in the quotes folder so a reprint reads nothing at all, and a card whose photograph cannot be fetched is printed as a `no photo` box and counted in the report rather than left as a gap. Each card's title is also a **link to that card's page on your website**, so a quote opened on a phone is a shortlist the customer can browse - the link is over the title and nothing else, so clicking a price never opens a product page, and a card that never had a page prints without a dead link. **Copy it as text** puts the same quote on the clipboard for a text message or Messenger, where a PDF is not much use. Without WooCommerce keys everything except the search and the order still works - the quote saves, prints and copies, and **Turn into an order** opens `woo-keys.txt` instead of failing.
- Print the sheet a packed order travels with from **Print an order**, the last button of the **After a sale** section on both the task launcher and the tabs view - an order is printed after it is sold, so it belongs with the after-a-sale jobs. One search box takes all three ways an order is remembered: the number on the dashboard (`1042` or `#1042`), the customer's name, or the name of a card that was in it. Every match is listed with the reason it is there - the number matched, the shop's own order search answered, a card's name matched after being looked up among the products and each match asked which orders hold it, or it is a quote saved in your quotes folder - so the wrong sheet cannot be printed quietly. Click a row and press **Save the order as a PDF...** (or double-click it) for the same paper the quote uses: your logo and colour, the order's own number, its state in words, the day it was paid, the delivery address, **a picture of every card**, the totals, the notes and a PACKED BY / DATE line. It is saved beside the quotes in the orders folder and opened, and printing it changes nothing on the website: the order is read, never written. Without WooCommerce keys - or when the shop will not answer - the quotes folder still answers the search, because a quote carries the customer's name and every card's name, and the sheet is printed from the quote's own record with a note saying so. The cards' pictures are downloaded once and kept, so a reprint reads nothing, and a card whose picture cannot be fetched is printed as a `no photo` box and counted rather than stopping the sheet. Without keys the website's order list is one button away from the same row.
- The optional CanadianShopper plugin adds draft actions directly to the running pipeline: `v` previews all vendor drafts without changes and returns to the choices, `y` publishes ready drafts after the same `PUBLISH` confirmation used by the app, and `n` (or Enter) skips draft review/publishing. The plugin's publisher runs as its own process, so its "type PUBLISH" question used to be swallowed and leave the run looking frozen. Plugin **1.0.27 or newer** streams it - the question, and the typed answer, now cross the console like any other prompt - and Alex Collect tells every tool it starts that a console is reading its output (`ALEX_COLLECT_NESTED`), which is what lets the plugin add progress around its own children. The version is read from the plugin's manifest, never assumed: with anything older the console says before the plugin takes over that the question stays hidden there, and if the run really does go quiet after *Publishing ready CanadianShopper drafts* for 20 seconds it says what to do - type PUBLISH and press Send, or press Stop and use the card-pipeline panel's **Publish ready drafts**, which is the same publisher with a prompt that is always visible. Photo wiring then continues without an extra post-import Enter prompt. The same **Preview drafts** and **Publish ready drafts** buttons remain in the card-pipeline and **Import / publish drafts** panels; the app button also requires its confirmation dialog. No bookmarklet is needed.
- Re-run one marketplace at a time from **Re-run a marketplace step**, which sits in the **Sell a new batch** section because that is the batch it rebuilds: rebuild just the WooCommerce CSV, the CanadianShopper CSV, the Facebook feed/export, or the eBay Quick List from the AI reply already on disk. Each button rebuilds only its own output and never moves or renames the images again, so a mistyped answer at one step no longer means repeating the whole batch. If no AI text is found the button asks for the file.
- Install optional plugins from a local ZIP using **Plugins** in the menu bar.

Uploading a photo needs a WordPress **Application Password** (Users > Profile > Application Passwords): the WooCommerce consumer keys cannot reach the media library, and setting a product photo needs Read/Write keys rather than Read-only. Application Passwords need HTTPS. Without those two lines the app still names and saves the image; you attach it in the media library. With them, each uploaded photo is also filed under the product it belongs to, so the media library shows it attached instead of listing it under **Unattached**.

The core continues to work without any plugins. The CanadianShopper integration is maintained separately and is **not included** in this repository or the core download.

## Install and run

### Windows

You can install from source or build an Inno Setup installer:

- **Run from source:** Install Python 3 with Tcl/Tk, run `python -m pip install -r requirements.txt`, then double-click `START Alex Collect.bat`.
- **Inno Setup:** See [`installer/README.md`](installer/README.md). It documents a small setup for PCs with Python and a separate setup that installs a private Python runtime. The bundled setup still needs internet during installation to download Python packages.

Both installers package only the public core. CanadianShopper remains a separate plugin ZIP and is installed from the Plugins menu item.

### Linux

Install Python 3, Tkinter, and the requirements. On Debian/Ubuntu:

```sh
sudo apt install python3 python3-tk python3-pip
python3 -m pip install --user -r requirements.txt
./install-linux.sh
./start-alexcollect.sh
```

## Plugins

Choose **Plugins** from the menu bar to install a trusted plugin ZIP, enable or disable it, or remove it. Plugin code is not sandboxed and runs with your account's permissions; install only packages from sources you trust. Alex Collect does not download plugins automatically.

The CanadianShopper plugin is a separate, privately maintained package and is not part of the public core. Plugin developers can start with [the plugin API](docs/PLUGIN-API.md).
